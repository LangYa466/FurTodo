# FurTodo Server

A serverless to-do backend built for offline-first clients. Every entity (task, list, folder, tag, settings) is a row in PostgreSQL; clients keep a local database as the source of truth and sync over a small push/pull protocol.

Built on Cloudflare Workers, Hyperdrive, and Drizzle ORM.

## What it does

- **Offline-first sync** — `POST /v1/sync/push` batches mutations, `GET /v1/sync/pull` returns changes after a cursor. Field-level last-writer-wins by client edit time, so an offline device never overwrites a newer edit.
- **Trash with 30-day retention** — deletes are tombstones, restorable, and eventually purged. Clients resync when a tombstone they missed has been purged.
- **Views** — today (My Day, overdue, due today, focus scoring), upcoming, and the Eisenhower matrix.
- **Quick capture** — parse one line into a task: `明天下午3点 给王先生打电话确认报价 #电脑前 @工作 !高 ~15m`.
- **Recurring tasks** — completing one spawns the next occurrence with a deterministic id, so retries cannot duplicate it.
- **Web Push reminders** — a per-minute cron sends due reminders.
- **GitHub OAuth (PKCE)** — sign-in requires a GitHub account at least a year old, which keeps throwaway accounts out.
- **Per-user quotas** — daily request, read, write, login, and push caps bound the database work one account can cause.

## Stack

| Concern                | Choice                                                          |
| ---------------------- | --------------------------------------------------------------- |
| Runtime                | Cloudflare Workers (TypeScript)                                 |
| HTTP                   | Hono + `@hono/zod-openapi` (OpenAPI 3.1 at `/openapi.json`)     |
| Database               | PostgreSQL via Hyperdrive, node-postgres driver                 |
| ORM                    | Drizzle ORM, migrations generated by drizzle-kit                |
| Per-user serialisation | one transaction holding `SELECT ... FOR UPDATE` on the user row |
| Tests                  | Vitest with a real PostgreSQL 19 container                      |

## API

Full client integration guide: [`docs/INTEGRATION.md`](docs/INTEGRATION.md). Interactive docs are served at `/docs`.

| Area                   | Endpoints                                                                                                                                                       |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auth                   | `GET /v1/auth/github/authorize`, `GET /v1/auth/github/callback`, `POST /v1/auth/token`, `POST /v1/auth/logout`, `GET /v1/auth/sessions`, `POST /v1/auth/tokens` |
| Account                | `GET /v1/me`, `GET /v1/usage`, `GET                                                                                                                             | PATCH /v1/settings`                                  |
| Tasks                  | `GET                                                                                                                                                            | POST /v1/tasks`, `GET                                | PATCH | DELETE /v1/tasks/{id}`, `POST /v1/tasks/{id}/complete`, `POST /v1/tasks/{id}/uncomplete`, `POST /v1/tasks/{id}/restore` |
| Lists / folders / tags | same shape as tasks under `/v1/lists`, `/v1/folders`, `/v1/tags`                                                                                                |
| Views                  | `GET /v1/views/today`, `/upcoming`, `/matrix`                                                                                                                   |
| Sync                   | `POST /v1/sync/push`, `GET /v1/sync/pull`                                                                                                                       |
| Capture                | `POST /v1/capture`                                                                                                                                              |

All timestamps are UTC ISO 8601; dates are `YYYY-MM-DD`.

## Deploy

1. Create the Hyperdrive config with caching disabled — sessions, quotas, and sync must read their own writes:

   ```sh
   npx wrangler hyperdrive create furtodo-db --caching-disabled --connection-string="$DATABASE_URL"
   ```

2. Put the printed id in `wrangler.jsonc` in place of `REPLACE_WITH_HYPERDRIVE_CONFIG_ID`, and set `PUBLIC_BASE_URL`, `routes`, and `ALLOWED_REDIRECT_URIS` for your domain.

3. Apply the migrations to the same database:

   ```sh
   DATABASE_URL=... npm run db:migrate
   ```

4. Set the secrets:

   ```sh
   npx wrangler secret put GITHUB_CLIENT_ID
   npx wrangler secret put GITHUB_CLIENT_SECRET
   npx wrangler secret put TOKEN_SECRET          # at least 32 chars; keys token HMACs and sealed state
   npx wrangler secret put VAPID_PUBLIC_KEY
   npx wrangler secret put VAPID_PRIVATE_KEY
   ```

5. `npm run deploy`

## Develop

```sh
bun install

# Point Hyperdrive at a local PostgreSQL and apply the migrations.
export CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE=postgres://...
DATABASE_URL=postgres://... npm run db:migrate

npm run dev
```

`npm test` runs the unit tests plus the Worker integration tests. The integration tests start a throwaway `postgres:19-alpine` container with Docker or Podman; set `TEST_DATABASE_URL` to use a database you supply instead (it is migrated in place, so point it at a disposable one).

## Scripts

| Script                         | Purpose                                      |
| ------------------------------ | -------------------------------------------- |

| `npm test`                     | Unit and Worker integration tests            |

| `npm run db:generate`          | Generate a migration from `src/db/schema.ts` |
